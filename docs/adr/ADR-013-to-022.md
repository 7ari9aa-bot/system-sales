# Architecture Decision Records (ADR-013 to ADR-022)

## ADR-013: Tenant Context Across Execution Modes

### Status
Accepted

### Context & Problem Statement
The system executes in four distinct operational modes:
1. Synchronous HTTP request/response via FastAPI
2. Asynchronous background workers consuming from Redis Streams
3. Scheduled jobs and reconciliation pollers
4. Realtime Server-Sent Events (SSE) streaming connections

Without a strictly unified protocol for tenant context propagation, execution can bypass PostgreSQL Row-Level Security (RLS) or accidentally bleed tenant data.

### Decision
Tenant context is unconditionally enforced at every layer:
1. **HTTP Requests**: Derived strictly from verified JWT `tenant_id` claim in `TenantCtxDep`. Sets PostgreSQL session GUC `app.tenant_id` via `bind_tenant(session, tenant_id)` on every acquired connection.
2. **Workers & Outbox Relay**: Every event payload on Redis Streams contains `tenant_id`. The worker invokes `bind_tenant(session, event.tenant_id)` prior to executing domain logic.
3. **Scheduled Jobs**: The `scheduled_jobs` table records `tenant_id`. The poller binds the tenant before dispatching to the registered job handler.
4. **SSE Realtime**: Double-enforced — the connection query token authenticates the user and tenant, and the event filter checks `event.tenant_id == client.tenant_id` before fanning out to the client.

### Consequences
- **Positive**: Zero risk of tenant cross-talk or data leakage. Complete RLS enforcement even in background workers.
- **Negative**: Small overhead of executing `SET LOCAL app.tenant_id = :id` per session checkout.

## ADR-014: Conversation Serialization

### Status
Accepted

### Context & Problem Statement
Inbound customer messages arrive concurrently across multiple channels (WhatsApp, Telegram, Webchat). If multiple webhooks or agent workers process messages for the same conversation concurrently, race conditions cause disordered message threads, broken AI context memory, and duplicate replies.

### Decision
Conversation mutations are serialized per conversation:
1. **Advisory Locks**: Acquire PostgreSQL transaction advisory lock `pg_try_advisory_xact_lock(hashtext('conv:' || conversation_id))` during message ingestion and state transitions.
2. **Channel Deduplication**: `uq_messages_tenant_channel_message_id` constraint guarantees idempotency per provider message ID.
3. **Sequence & Keysets**: Message history is ordered strictly by `(created_at, id)` keyset pagination to maintain chronological coherence across all clients and AI context builders.

### Consequences
- Eliminates out-of-order message processing and split-brain AI agent loops.
- Lock duration is kept to single-digit milliseconds (ingest write + outbox record only).

## ADR-015: Event Consumer Idempotency

### Status
Accepted

### Context & Problem Statement
Redis Streams and distributed worker pools guarantee *at-least-once* delivery. Network blips, worker restarts, or consumer rebalancing will cause duplicate event deliveries.

### Decision
Adopt the **Transactional Deduplication & Processed Events Pattern**:
1. Every consumer maintains idempotency using the `processed_events` table within the same database transaction that executes domain effects.
2. An event is marked processed via `INSERT INTO processed_events (tenant_id, consumer_group, event_id, processed_at) VALUES (...) ON CONFLICT DO NOTHING`.
3. If zero rows are inserted, the event has already been executed; the worker commits/acknowledges the Redis stream offset immediately without re-executing domain side-effects.

### Consequences
- Full idempotency across all stream consumers (messaging, notifications, billing, analytics).
- Transient duplicate stream messages cannot cause duplicate billing charges, double message dispatch, or duplicate orders.

## ADR-016: Outbound Message Delivery State Machine

### Status
Accepted

### Context & Problem Statement
Outbound messages dispatched to third-party providers (Meta Cloud API, Telegram Bot API) can fail, time out, or be dropped in flight. A blind retry on timeout could result in sending the same message (or promotional broadcast) multiple times to a customer.

### Decision
Implement the definitive **Delivery State Machine**:
```
queued ──→ sending ──┬──→ sent ──┬──→ delivered ──→ read
                     │           └──→ failed
                     ├──→ failed (explicit provider error)
                     └──→ unknown (timeout / dropped connection)
                               │
                               └──→ Reconciled via Webhook receipt or
                                    Reconciliation Worker (never blind retry)
```
1. `sending` is claimed via `FOR UPDATE SKIP LOCKED`.
2. Provider network timeouts transition the message to `status = 'unknown'`.
3. An `unknown` message is **never blindly resent**. It awaits delivery receipts or is resolved by the `reconcile_unknown_messages` worker.

### Consequences
- Prevents embarrassing duplicate customer messages and spam penalties from Meta.
- Requires explicit reconciliation worker and status receipt webhooks.

## ADR-019: Human Approval Workflow

### Status
Accepted

### Context & Problem Statement
AI agents have tool access to sensitive domain operations (issuing refunds, large discounts, sending bulk campaigns, modifying stock). Direct execution without oversight presents business and compliance risk.

### Decision
Introduce the **Two-Phase Approval Pattern**:
1. When an AI agent decides to execute a high-risk tool (as configured in `ApprovalPolicy`), it does not execute immediately.
2. The agent creates an `approval_requests` record in state `pending` with the exact tool name, parameters, and rationale.
3. An in-app `Notification` is sent to authorized staff/managers.
4. Once a human manager clicks "Approve" via the UI or API, the execution is dispatched asynchronously with the approving user ID recorded in the audit log.
5. If rejected or expired (SLA timeout), the action is cancelled safely.

### Consequences
- High security and human-in-the-loop guarantee for critical financial and inventory operations.
- Latency for sensitive operations is tied to human response time.

## ADR-022: Sagas / Process Managers

### Status
Accepted

### Context & Problem Statement
Complex business processes span multiple modules: for example, checkout involves Order Placement -> Stock Reservation -> Payment Authorization -> Reservation Conversion -> Outbound WhatsApp Confirmation. Distributed transactions across microservices or complex distributed modules without coordination cause partial failures (e.g. money deducted but stock out).

### Decision
Implement **Database-Backed Orchestration Sagas**:
1. PostgreSQL is the central state store for all core domains (single database, modular schema).
2. Sagas execute within controlled transaction boundaries:
   - Order creation creates `inventory_reservations` in status `active` with a 15-minute TTL.
   - Payment capture converts the reservation to `converted` and marks order `confirmed`.
   - Payment failure or timeout marks reservation `cancelled` or leaves it to expire via background maintenance worker.
3. Every step records an audit log and outbox event to keep analytics and realtime clients in sync.

### Consequences
- Complete financial and inventory consistency without requiring distributed 2PC (two-phase commit).
- Transparent audit trail for order lifecycles.
