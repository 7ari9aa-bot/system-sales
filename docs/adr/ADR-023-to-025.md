# Architecture Decision Records (ADR-023 to ADR-025)

## ADR-023: Customer 360° Identity Merge & Deduplication

### Status
Accepted

### Context & Problem Statement
Customers interact across fragmented channels (WhatsApp phone number, Webchat guest session, Telegram username, online store checkout email). Without a structured identity resolution strategy, the system creates duplicate customer records, fragmenting conversations, order history, and lifetime value analytics.

### Decision
Implement an **Audited Identity Merge Service**:
1. **Identities Model**: `customer_identities` table links external identifiers (`channel`, `identifier_type`, `identifier_val`) to a canonical `customer_id`.
2. **Deterministic & Probabilistic Resolution**: When inbound events arrive, lookup existing identities by exact phone/email.
3. **Merge Protocol**:
   - Primary customer record is retained; secondary customer record is marked merged with `merged_into_id` pointer.
   - Child entities (`conversations`, `orders`, `addresses`, `consents`, `tags`) are reparented to the primary customer.
   - An immutable record is created in `identity_merge_events` containing the initiator, source customer, target customer, and snapshot of reparented entities.
4. **Idempotency**: Reparenting uses transaction locks to avoid race conditions during concurrent webhook deliveries.

### Consequences
- True Unified Customer 360° view across all communication channels.
- Fully reversible and auditable merge history complying with data lineage requirements.

## ADR-024: Inventory Reservations & TTL-Based Auto-Release

### Status
Accepted

### Context & Problem Statement
In high-demand sales and flash campaigns, overselling occurs when stock is not held between order creation and payment confirmation. If stock is immediately deducted before payment, abandoned carts permanently deplete available inventory.

### Decision
Implement **Two-Phase Inventory Reservations with Leases**:
1. **Active Reservation**:
   - Placing an order creates an `inventory_reservations` row with `status = 'active'` and a 15-minute lease expiration (`expires_at = now() + 15 min`).
   - Available stock query calculates: `available = physical_balance - sum(active_reservations)`.
2. **Resolution Lifecycle**:
   - **Payment Succeeded**: Reservation status transitions to `converted`, and an `inventory_movements` row is committed with `movement_type = 'sale'`.
   - **Payment Failed / Cancelled**: Reservation status transitions to `cancelled`, instantly freeing up stock.
   - **Abandoned / Expired**: A scheduled maintenance worker runs every minute to transition overdue reservations to `expired`.
3. **Optimistic Concurrency**: Stock balance updates utilize `version` column increments (optimistic locking) to detect and prevent race conditions.

### Consequences
- Prevents stock overselling and eliminates ghost inventory depletion from abandoned carts.
- Zero distributed lock contention; relies on database-level row locking and timestamp evaluations.

## ADR-025: Inbound Channel Webhook Deduplication & Cryptographic Verification

### Status
Accepted

### Context & Problem Statement
External messaging providers (Meta WhatsApp Cloud API, Telegram Bot API, Custom Webhooks) retry webhook delivery aggressively on network timeouts or delayed HTTP 200 responses. This can cause duplicate message insertion, duplicate AI agent executions, and duplicate order processing. Furthermore, untrusted requests could spoof webhook payloads.

### Decision
Implement a **Strict Inbound Gateway Pipeline**:
1. **Cryptographic Signature Verification**:
   - Every provider adapter verifies signature headers before parsing payload:
     - WhatsApp: `X-Hub-Signature-256` HMAC-SHA256 verified against channel app secret.
     - Telegram: `X-Telegram-Bot-Api-Secret-Token` matched against registered webhook secret.
     - Custom: HMAC-SHA256 signature against tenant integration secret.
2. **Two-Tier Deduplication**:
   - **Tier 1 (Redis Cache)**: Set atomic key `dedupe:msg:{provider}:{external_message_id}` with a 24-hour TTL using `SET NX`. If key exists, immediately acknowledge with HTTP 200 without reprocessing.
   - **Tier 2 (PostgreSQL Unique Constraint)**: `inbound_message_dedupe` table with `UNIQUE(tenant_id, provider, external_message_id)` guarantees persistence idempotency even if Redis restarts.
3. **Fast Acknowledgement**: The webhook endpoint enqueues raw events to Redis Streams `message.inbound` and returns HTTP 200 within 200ms.

### Consequences
- Absolute protection against duplicate messages, duplicate billing, and spoofed webhook calls.
- Fast webhook turnaround time preventing provider timeout retries.
