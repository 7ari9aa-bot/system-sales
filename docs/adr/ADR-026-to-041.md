# Architecture Decision Records (ADR-026 to ADR-041)

## ADR-026: Auth / Platform Admin Separation

### Status
Accepted

### Context & Problem Statement
The platform serves multiple commercial tenants (e-commerce businesses). Platform super-administrators (internal operations, billing managers, system engineers) need governance access without being regular tenant members, and tenant owners must never gain platform-level capabilities.

### Decision
Strictly separate Platform Administration from Tenant Roles:
1. **User Identity Flag**: `users.is_platform_admin` (boolean) is stored on the global `users` table and is only settable via direct database provisioning or dedicated internal CLI commands.
2. **Dedicated Routes**: Platform endpoints are segregated under distinct prefixes (e.g. `/platform/...`, `/billing/platform/...`) guarded by `require_platform_admin` dependency.
3. **Tenant Boundary**: Platform admins do not bypass Row-Level Security by default; when inspecting tenant data, they must explicitly switch tenant context, which emits an immutable `AuditLog` row with action `platform.impersonate_tenant`.

### Consequences
- Clean separation of concerns between multi-tenant SaaS application logic and SaaS infrastructure management.
- Complete regulatory audit trail for platform staff operations.

## ADR-029: Durable Event Log vs Outbox

### Status
Accepted

### Context & Problem Statement
Systems that rely solely on in-memory message queues or direct broker calls suffer from the dual-write problem: if the database commits but broker publish fails, data is lost; if broker publish succeeds but database fails, phantom events are processed.

### Decision
Implement a **Dual-Tier Event Architecture**:
1. **Transactional Outbox (`outbox_events`)**:
   - Written within the exact same database transaction as the business entity changes.
   - Polled by the `OutboxRelay` background process every 500ms using `FOR UPDATE SKIP LOCKED`.
   - Dispatched to Redis Streams topic streams (`message.events`, `conversation.events`, `order.events`, etc.).
   - Rows are marked published and pruned after delivery.
2. **Durable Event Log (`event_log`)**:
   - An append-only, permanent audit log of all domain events for compliance, replay, and long-term business intelligence.
   - Immune to stream truncation and TTL policies.

### Consequences
- Guaranteed zero event loss even during sudden process crashes or Redis downtime.
- Asynchronous stream propagation decouples database write performance from external consumers.

## ADR-039: Runtime Topology / Redis Failure

### Status
Accepted

### Context & Problem Statement
Redis serves as the fast ephemeral event bus and cache (Redis Streams, Rate Limiting, Realtime SSE buffer). If Redis becomes temporarily unreachable or suffers node failure, core business operations must not crash.

### Decision
Apply **Graceful Degradation and Redis Non-Fatal Fallback**:
1. **Source of Truth**: PostgreSQL is the sole durable source of truth. Core transactional flows (login, message ingestion, order creation, payments) write to PostgreSQL and commit first.
2. **Rate Limiting Fallback**: If Redis fails during rate-limit checks, the rate limiter fails OPEN with a warning log, ensuring paying customers can continue checkout rather than experiencing 500 errors.
3. **Outbox Recovery**: When Redis recovers, the `OutboxRelay` resumes reading unpublished `outbox_events` from PostgreSQL and resumes streaming from the exact failure point without data loss.
4. **SSE Realtime**: SSE clients receive automatic exponential backoff reconnects and resume from their last acknowledged event ID cursor.

### Consequences
- High resilience: temporary Redis failure degrades realtime notifications to polling, but business-critical transactions continue unhindered.

## ADR-041: Entitlement Enforcement

### Status
Accepted

### Context & Problem Statement
Different SaaS tenants subscribe to different tiers (Starter, Growth, Enterprise) with quotas on active users, monthly orders, AI tokens, and features (e.g. advanced marketing attribution, custom domains). Enforcing quotas only at the UI layer is insecure; enforcing them haphazardly in database queries leads to code duplication.

### Decision
Implement **Centralized Entitlement Checks in Domain Services**:
1. **Entitlements Table**: `entitlements` defines tenant quotas, current usage counters, and feature flags.
2. **Pre-flight & Post-flight Checks**:
   - User creation checks `current_users < max_users`.
   - AI generation checks `AI Gateway` hard budget caps (`BudgetPolicy`).
   - Feature-specific APIs check `check_feature_enabled(session, tenant_id, "marketing_automation")`.
3. **HTTP Status 402 / 403**: When quotas are exceeded, the API returns a structured error with code `ENTITLEMENT_EXCEEDED`, including current usage and upgrade link for seamless self-service checkout.

### Consequences
- Predictable monetisation enforcement across all API and AI agent paths.
- Clean upgrade funnel from free/trial tiers into paid plans.
